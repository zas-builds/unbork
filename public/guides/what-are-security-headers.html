What are security headers, and is my app missing them?

Written 21 November 2026. Every source below was opened and checked on the date given.

Short answer: they are short instructions your host sends alongside every page, telling the browser to insist on a secure connection, to refuse to be loaded inside somebody else’s website, and not to guess what kind of file it has been handed. Nothing breaks without them. They close off a few specific attacks, and that is all they do.

If yours are missing you are in ordinary company rather than in trouble. Of 30 published Lovable apps we checked from outside on 18 November 2026, 29 were missing at least one. That is why our own report never turns red over a header: it lists them under “worth adding”, next to the things that actually need doing.

The three we look for, and what each one stops

Strict-Transport-Security. Tells the browser to always use the secure version of your site in future. Without it, somebody’s very first visit can be sent over an unprotected connection before the redirect to https happens, and that first request is the one worth intercepting.

X-Frame-Options (or frame-ancestors in a content security policy). Stops another website loading your app inside its own page. Without it, someone can wrap your sign-in screen in a copy of your site and collect what people type into it.

X-Content-Type-Options: nosniff. Stops the browser guessing what kind of file it has been sent. Guessing wrongly is how a file that was meant to be an image ends up being run as code.

None of these is urgent, and none of them fixes anything that is currently broken. If your report also lists something under “fix now”, do that first.

Why almost every app is missing them

Because headers are not part of your app. They are added by whatever serves your pages, after your code has finished running. Your builder can write perfect code and still produce a site with no headers at all, because the setting lives in a configuration file for your host, or in your host’s own defaults, and nobody told the builder to write one.

This matters for a practical reason: whether you can do anything about it depends entirely on where your app is published, not on what your app does.

If your app is on your own Netlify deployment

This is the easy case. Netlify reads custom headers either from a file called _headers in your published folder, or from a netlify.toml file at the top of your project. In netlify.toml the shape Netlify documents is a for pattern and then the values:

[[headers]]
  for = "/*"
  [headers.values]
    Strict-Transport-Security = "max-age=31536000; includeSubDomains"
    X-Frame-Options = "DENY"
    X-Content-Type-Options = "nosniff"

Commit that, let it redeploy, and run the check again. If your app needs to be embeddable inside another site on purpose, use SAMEORIGIN in place of DENY, which is the value Netlify’s own example uses. The file names and the format are from Netlify docs: Custom headers, read on 21 November 2026.

If your app is on your own Vercel deployment

Vercel takes the same idea through a headers setting in its project configuration file. We are not going to print a snippet here: we tried to read Vercel’s current reference for that field on 21 November 2026 and could not get the page to render for us, and a configuration file that is nearly right is worse than none. Open Vercel docs: Project configuration and look for headers, or use the prompt below, which tells your builder to go and read that page itself rather than remembering.

If your app is on a lovable.app address

Then as far as we can tell there is nothing for you to do, and nothing you have done wrong. Lovable hosts those pages, so Lovable decides what headers they carry. We went looking through Lovable’s own security documentation on 21 November 2026 for a way to set response headers on a published app and did not find one. Our 30-app count is consistent with that: when 29 of 30 sites on one platform are missing the same setting, the likeliest explanation is the platform, not 29 careless builders.

So if you are on Lovable’s hosting, treat this as a question for Lovable rather than a job for you. If you do find a way to set them there, tell us and we will correct this page.

The prompt, if you deploy the app yourself

Paste this into Lovable, Bolt or Cursor. It makes the builder read your host’s current documentation rather than writing a config from memory, which is the usual way these end up wrong.

My app is deployed to [Netlify / Vercel]. I want three response headers on every page:
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Frame-Options: DENY
X-Content-Type-Options: nosniff

Please:
1. Tell me which configuration file my host reads for custom response headers, and check that against my host's current documentation rather than from memory. Quote the page you used.
2. Add exactly those three headers for all paths, in that file, changing nothing else about my routing or build settings.
3. If my app is meant to be embedded in another site, say so and use SAMEORIGIN instead of DENY, and explain why.
4. List every file you changed, and tell me how to confirm the headers are live after I redeploy.

How to tell whether it worked

Redeploy, then run the free check again. The three headers move from “worth adding” into the list of things that are fine. Nothing else about your report should change, and if something else does change, it was not the headers that did it.

What we can and cannot tell you

Our check reads what your live site sends back to an ordinary visitor, so headers are one of the few things we can see completely and be certain about. What we cannot see is why they are missing, or whether your host will let you add them. This page is information, not a security audit and not legal advice.
