What is Row Level Security, and is mine on?

Written 20 November 2026. Every source below was opened and checked on the date given.

Short answer: Row Level Security is a set of rules that live inside your database and decide, for every single request, which rows it is allowed to see or change. Without it, the public key in your app’s JavaScript is a key to the whole table. Supabase puts it plainly: “A table in an exposed schema without RLS is readable and writable by any role with a grant on it.”

You cannot find this out from outside, and neither can we. It takes about five minutes inside your Supabase project, and it is the single most valuable five minutes available to anyone who built an app without reading the code.

Why this is the question that actually matters

Your app talks to your database straight from the visitor’s browser, using a publishable key. That key is meant to be public, and on its own it is harmless. It is harmless because Row Level Security stands between it and your rows. Switch those rules off and the same key that loads your home page will also hand over your whole customers table to anyone who asks for it.

This is the difference between “my key is exposed” and “my data is exposed”. The first is normal. The second is the one that ends up on the news.

What a policy actually is

A policy is a rule attached to one table, and the database runs it every time anything touches that table. Supabase’s own description is the clearest one: “Think of a policy as adding a WHERE clause to every query.” So a rule that says “people can see their own to-dos” quietly turns every request into “… where this row belongs to you”, whoever wrote the request and whatever they asked for.

Because the rule lives in the database rather than in your app, it still applies when someone skips your app entirely and calls the database directly, which is exactly what an attacker does.

Turning it on is one line

alter table public.your_table enable row level security;

Run that in the SQL Editor in your Supabase dashboard, once for every table. Supabase notes what happens next: “Once RLS is enabled, no data is accessible through the API when using a publishable key, until you create policies.” In other words it locks the door first and asks you to cut the keys afterwards, which is the right way round. Expect parts of your app to go blank until you have written the policies, and do this on a day when you have an hour, not five minutes before a demo.

The part nearly everybody misses: grants

Two separate checks run before anyone touches a table. A grant decides whether a role may run an operation on the table at all. A policy decides which rows that operation applies to. Supabase is explicit that one does not replace the other: “Adding policies doesn’t take those grants back. A table protected only by policies still hands anon an insert path if you never revoke the grant.”

On existing projects a new table in public starts with every privilege already granted to the signed-out role, the signed-in role and the service role. So the full job for a table is three lines, not one:

alter table public.your_table enable row level security;
revoke all on table public.your_table from anon, authenticated;
grant select, insert, update, delete on table public.your_table to authenticated;

That last line is the one to think about. Grant each role only what your app genuinely lets it do. If signed-out visitors are never meant to read a table, they should hold no grant on it at all.

Write one policy per operation

Reading, creating, changing and deleting are four different questions, and Supabase asks you to answer them separately: “Postgres does not accept multiple operations in one for clause, and a for all policy hides which operation each rule was meant to cover.” If your builder produced a single for all policy, that is a smell, not a shortcut.

Two details from the same page that cost people real data. Name the role every policy applies to with a to clause, so a rule written for signed-in users never runs for strangers. And an update needs both halves: using decides which existing rows may be changed, with check decides what the changed row is allowed to look like. Leave out the second and a user can edit their own row into somebody else’s.

Three traps in vibe-coded apps

  • Views walk straight past your rules. “Views bypass RLS by default because they are usually created with the postgres user… A view over a protected table hands out every row its policies were meant to withhold.” On Postgres 15 and above the fix is to create the view with (security_invoker = true).
  • Do not build rules on data the user can edit. Anything in raw_user_meta_data can be changed by the signed-in user themselves, so a policy that trusts it is not a policy. Supabase: “raw_app_meta_data cannot be updated by the user, so it’s a good place to store authorization data.”
  • A secret key ignores all of this. The secret or service_role key runs as a role that bypasses Row Level Security by design: “Never use a secret key in the browser or expose it to customers.” If one is in your front-end code, no amount of policy work helps. How to tell your keys apart.

How to check yours, in order

  1. Open your Supabase project and go to the Table Editor. List every table your app reads or writes.
  2. For each one, in the SQL Editor, enable Row Level Security, revoke the grants and grant back only what that table needs, using the three lines above.
  3. Write a policy for select, insert, update and delete on each table, naming the role in a to clause.
  4. Check the views as well as the tables.
  5. Prove it, rather than assuming it. Supabase’s own instruction is blunt: “Until the suite passes, you don’t know whether the policies do what you intended.” The documented way is a test file per table under supabase/tests/, run with supabase test db. If that is beyond you today, the next best thing is to sign out of your own app in a private window and try to reach data that is not yours.

The prompt to paste into your builder

Copy this as it is. It makes the builder show you the facts before it changes anything, which is the only way to keep an AI honest about a database.

Before changing anything, inspect my Supabase project and list for me, as a table:
1. Every table in the public schema.
2. Whether Row Level Security is enabled on each one.
3. Every policy on each one, with the operation it covers and the role it applies to.
4. Which grants anon and authenticated hold on each one.
5. Every view, and whether it was created with security_invoker = true.
Show me that list and wait for me to confirm it before you write any SQL.

Then, for each table I confirm, in one migration:
- enable row level security
- revoke all grants from anon and authenticated
- grant back only the operations I tell you that role needs
- create a separate policy for select, insert, update and delete, each naming its
  role with a "to" clause, and each update policy having both using and with check

Rules: do not use "for all". Do not write a policy that reads raw_user_meta_data.
Do not create a security definer function in an exposed schema. Where you are not
sure what a table is for, write [CHECK] and ask me instead of guessing. List every
[CHECK] at the end. Do not touch my app code in the same change.

What we can and cannot tell you

Our free check reads the JavaScript your live site serves and tells you which keys are in it, which is the half of this that is visible from outside. It cannot see your tables, your policies or your grants, and we are not going to pretend otherwise: nobody can tell you your database is locked without looking inside your project. When we checked 35 live Lovable apps on 18 November 2026, not one of them had leaked a secret key, and we still could not say whether a single one of those databases was safe.
