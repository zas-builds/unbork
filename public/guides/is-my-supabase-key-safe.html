Is my Supabase key safe in the browser?

Written 18 November 2026. Every source below was opened and checked on the date given.

Short answer: if the key starts with sb_publishable_, or it is the older anon key, it is meant to be public and Supabase says it is safe to expose. If it starts with sb_secret_, or it is the service_role key, it is an emergency: that key ignores your rules, and anyone who finds it can read, change and delete everything.

Everybody can read every line of JavaScript your site sends. There is no such thing as a key hidden in a web page.

Which key do I have?

  • sb_publishable_… — publishable. Supabase’s own table of keys describes it as “Safe to expose online: web page, mobile or desktop app, GitHub actions, CLIs, source code.”
  • sb_secret_… — secret. Server only. Supabase states plainly: “A secret key doesn’t work in a browser.”
  • A very long key beginning eyJ — one of the older pair, anon or service_role. Supabase says: “If a tool, tutorial, or AI assistant tells you to copy a long key that begins with eyJ, it was written for the legacy keys.” anon behaves like publishable; service_role behaves like secret and must never reach a browser.

All quotes from Supabase docs: API keys, read 18 November 2026.

The part most people miss

The publishable key is safe because of Row Level Security, not instead of it. Supabase’s own wording for where to use it is: “Anyone can read it, so it only reaches what Row Level Security allows.” Turn those rules off and the public key is a key to the whole table. So the question “is my key safe” is really two questions, and the second one matters more: are my tables locked?

Being straight about our own limits: a check from outside, including ours, can see which keys your site publishes. It cannot see your table rules. Nobody can tell you your data is safe without looking at your Supabase project, and anyone who says otherwise from the outside is guessing.

How to find out what your app publishes

Run a free check: it reads the JavaScript your live site serves and tells you which keys are in it and which of them matter. Or do it by hand: open your site, press Ctrl+U (Cmd+U on a Mac) to view source, open each .js file it links, and search for sb_secret, service_role and eyJ.

If you find a secret key in your front-end code

  1. Treat it as stolen. Create a new one in Supabase (Project Settings, then API Keys) and delete the old one. Hiding a published key does nothing: it is already out.
  2. Move whatever used it into server-side code, reading the key from an environment secret. Never give it a VITE_, NEXT_PUBLIC_ or REACT_APP_ prefix: Supabase’s own example is blunt about it, “Server-only. Never prefix these, or your bundler will ship the key.”
  3. Publish again and check the key has really gone.

What we see in the wild

On 18 November 2026 we checked 35 live Lovable apps from outside. None of them had a secret or service_role key in their front-end JavaScript. Publishable keys were common and are fine. So if your app is on Lovable’s own hosting, this is probably not where your problem is. The keys that leak tend to leak after somebody wires up a second service by hand.
